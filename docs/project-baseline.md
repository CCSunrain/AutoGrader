## 1. 项目定位与核心主张

**一句话**：把「一次不可追溯的模型打分」改造成「可检查、可修正、可回放的实验报告评阅流程」。

每一项评分建议必须绑定：**评分标准版本 + 报告版本 + 原文证据 + prompt 版本 + 模型 + 规则版本**。机器不确定时明确请求复核；最终成绩只能由教师发布。

## 2. 赛题与边界

| 产品形态 | 中文优先、桌面评阅优先、移动端可读的响应式 Web |
| 交付范围 | 课程与作业、Rubric、上传与解析、证据评阅、人工复核、发布、修订对比、班级分析、评估与过程档案 |

## 4. 技术栈与工程形态

| 层 | 选择 | 备注 |
| --- | --- | --- |
| 前端 | React 18 + TypeScript + Vite | TanStack Query 管服务端状态；浅灰背景 / 白面板 / 深蓝主操作色 |
| 后端 | FastAPI 模块化单体 | SQLAlchemy 2.0 + Alembic；Pydantic v2 结构化输出 |
| Worker | 独立进程（异步任务队列） | 与 Web 共享数据层，通过 PG 任务表 + 状态机恢复 |
| 数据库 | PostgreSQL | `tenant_id` 多租户隔离（RLS 可选） |
| AI | provider-agnostic adapter（OpenAI 兼容协议） | 结构化输出 = JSON Schema + 校验重试；凭据与模型经 `.env` 配置（base_url / api_key / model），见 §8 |
| 文件存储 | 对象存储 / 本地目录 | 报告原件 + 解析产物分开存 |
| 部署 | 前端静态 + 后端容器（Docker Compose） | 候选方案见 §10，待选定 |

### 评阅台布局（核心交互）

三栏：**左 = 评分项清单 ｜ 中 = 报告原文（证据高亮定位）｜ 右 = 模型建议 + 人工决定**。

## 5. AI 形态与质量原则

**AI 形态**：有限状态工作流（FSM）、工具权限受限、模型结构化输出、确定性规则算分。

**质量原则（不可违背）**：

1. 建议分必须取自量表允许档位，模型**不直接决定总分**。
2. `supported` / `missing` / `uncertain` 是三种不同状态，不得混同。
3. **引用存在 ≠ 语义支持**，必须独立核验引用与评分项之间是否真正对应。
4. 所有结果绑定：报告版本、解析版本、量表版本、prompt、模型、规则版本。
5. 已发布结果**不可原地修改**，纠错必须创建新 revision。
6. 所有外部能力、指标、用户反馈必须来自**真实验证**，不得虚构。
7. 证据不足、解析不全、内容矛盾、模型意见冲突 → 标记「待复核」，**不能自动判零分**。

## 7. 评估口径（真实测试集对比）

用同一真实测试集比较三种方案，报告：**准确性、覆盖率、错误放行、成本、耗时**。

| 方案 | 说明 |
| --- | --- |
| A. 一次性提示词打分 | 单次 prompt 直接给分 |
| B. 带证据检索 | 先定位原文再给建议 |
| C. 完整复核流程 | 循证 + 待复核 + 人工闭环（本产品） |

> 评估数据（自造模拟真实报告 + 教师 ground truth）与量化阈值定义见 §8。

## 8. 关键决策记录（逐项关闭）

| # | 决策项 | 结论 | 落实方式 |
| --- | --- | --- | --- |
| 1 | 真实测试集 + ground truth | **自造高质量「模拟真实」报告兜底**（排序 + 最短路径各一组，覆盖典型正确 / 缺失 / 数值矛盾 / 伪造引用等），配教师逐项人工评分作为 ground truth | `tests/fixtures/` 放样本，`evaluation/` 放标注与三方案脚本 |
| 2 | LLM 推理服务与额度 | LearnBuddy credits **可编程调用**，走 OpenAI 兼容协议；凭据放 `.env`，不硬编码 | provider-agnostic adapter + `pydantic-settings` 读 `base_url` / `api_key` / `model` |
| 3 | 在线部署 | **选定方案 A**（腾讯云 Lighthouse + Docker Compose，本地与线上同一套编排） | `docker-compose.yml` + `deploy/` 脚本；上线时需用户提供服务器 IP / SSH |

**已用默认值消解（可随时否决）**：

- PDF 解析：先走轻量路线（PyMuPDF 文本+表格+位置），保留 adapter 升级重型模型。
- 评测量化：档位偏差 ≥1 档即「错误」；「待复核」不计错误、单独统计覆盖率；成本 = token×单价，耗时 = 端到端秒。
- 档位结构：每评分项教师自定义 N 档（档名 + 分值），默认四档。
- 冲突检测：同模型多次调用 + 一致性校验，暂不引入多模型投票。

## 9. 竞赛侧约束（来自赛事手册）

- 作品须部署至浏览器环境，提供**可直接访问的在线链接**；提交完整源码仓库（GitHub/Gitee）；提交 LearnBuddy 历史对话记录。
- 评审维度：技术创新性 30% / 工程完整性 25% / AI 工具使用 25% / 用户体验 20%；加分项：跨专业组队 +2、社交媒体传播 +1。
- 知识产权归参赛者；本作品属方向一（教学管理），**开源非强制**，建议开源以增强透明度与可复现性；第三方库须在文档注明。

## 10. 在线部署方案（候选）

| 方案 | 全栈支持 | 成本 | 国内访问 | 打通方式 | 备注 |
| --- | --- | --- | --- | --- | --- |
| **A. 腾讯云 Lighthouse + Docker Compose** | ✅ 完整（前端 + 后端 + worker + PG） | 学生价约 ¥10–40/月，常有免费试用 | 快、稳 | 需一台轻量服务器 + SSH；我产出 `docker-compose.yml`/`deploy/` 脚本 | **推荐**，最贴合工程形态、可回放可排查 |
| B. CloudStudio 云托管（CloudBase Run） | 前端静态 ✅ / 后端容器 ✅ / PG 需改 MySQL 或云数据库 | 免费额度起 | 快 | 我有静态部署工具；全栈需额外容器化 + 数据库适配 | 腾讯生态，但 PG 需妥协为 MySQL 或容器内持久卷 |
| C. Render / Railway（海外 PaaS） | ✅ 完整（含托管 PG） | 免费 tier | 慢、不稳 | 需绑定 Git 仓库 + 账号 | 评审时可能打不开，仅作兜底 |

> 推荐 **A**：一条 `docker compose up -d` 拉起全部组件，公网 IP 即可访问（可选域名 + HTTPS）。若你暂无云服务器，B 是最快打通在线演示的腾讯生态路径，代价是数据库从 PG 适配为 MySQL。
>
> **已选定方案 A（2026-09-16）**：开发阶段用同一套 `docker-compose.yml` 在本地把全栈跑通（`docker compose up` 起 PG + 后端 + worker + 前端）；上线时把编排文件与 `.env.production` 拷到轻量服务器执行 `docker compose up -d --build` 即可，改动最小。
